# Unity game client and Windows state service

[Documentation home](../README.md) · [Gameplay](gameplay.md) · [Player assignment](player-assignment.md) · [Protocol](protocol.md) · [Physics](physics.md)

**Agreed design:** a doubles 2v2 game inspired by Wii Tennis, with automatic avatar movement, stationary human participants, gesture-driven toss/overhead serve, normal tennis scoring and two team-relative views. The host is the Windows laptop with RTX 5080. See the canonical [gameplay rules](gameplay.md), [assignment contract](player-assignment.md) and [ADR 0010](adr/0010-doubles-auto-movement-gameplay.md).

**Agreed engine selection:** implement the Windows game client, renderer and UI in **Unity with C#**, as requested on 2026-10-29 in [ADR 0012](adr/0012-unity-game-engine.md). This replaces the C++/SDL3 renderer proposal. The separate native C++20/CMake committed-state service remains a proposed implementation. Unity editor version, render pipeline, scripting backend and package versions must be verified and pinned during implementation. A Unity scene does not change the calibrated 2.5D tracking model or establish true 3D human tracking. Windows remains the primary deployment.

**Implemented:** documentation only; no game state service, match-rule runtime, renderer or gameplay tests exist yet.

## Match-state contract gap

The proposed v0.3 `motion.proto` snapshot carries the complete ball/avatar/serve/rally/score state, configuration references and ordered rule events. [S0 contract evidence](s0-baseline.md) covers generated host codecs, size/resource bounds and offline acceptance/rejection fixtures. A running service, target-platform codecs and gameplay behavior are not implemented. The required query/commit path uses the dedicated bounded TCP state stream described in [protocol](protocol.md).

Physics on the Pi calculates the ball, automatic avatar movement, serve transitions and score changes as one ordered candidate match state. The Windows state service validates and atomically stores the entire accepted match snapshot and events, then publishes that same version to the renderer. It does not run another scorer, independent avatar AI or separate ball integrator. The mandatory ball-state query/response stays in the processing path; its future match-version context must cover all state needed for a consistent decision.

## Separate state service from rendering

Keep the state service in a separate process from GPU inference and rendering. Its nonblocking socket loop responds independently of graphics-frame timing. It owns a single immutable current match snapshot under the planned extended contract and a bounded query/commit deduplication cache. No textures, neural inference, disk logging or UI event loop executes on that state path. This isolation reduces avoidable coupling; Windows scheduling still prevents a hard end-to-end timing guarantee.

Accept the physics writer through control setup with matching profile/schema hashes and a fresh epoch. For each required `ball_state_request`, return one atomic snapshot and exactly echo every transaction/query entry. A duplicate query within retention returns its original snapshot, not an unmarked newer response. A new query gets the current state. Track query send/receive times independently from render timestamps.

For `state_update`, validate sender/epoch/game session, exact base version, target tick, calibration, complete bounded event list and finite state. The extended match contract must validate roster/association, avatar, serve and score invariants as well as ball fields. Commit all events and final match state atomically or reject all; never publish a new score with an old serve/ball state. Increment state version once per batch. Return `state_commit_result` only after that operation. Rendering cannot advance authoritative ball, avatar or rule state.

Cache outcomes for 2 s, up to 512 batches; if retention cannot be honored, apply explicit backpressure/pause. Duplicate identical updates return the cached original result. A changed payload with the same update key is invalid. `commit_status` on the control connection resolves an uncertain update or returns unknown; a current snapshot cannot substitute for that answer. Fence old epochs after writer replacement and new game sessions after service restart.

## Unity implementation boundary

Build one Unity scene for the court, ball and four avatars, with two team cameras and the lobby, scoreboard and diagnostics UI implemented in C#. Both cameras consume the same committed match version. Unity's physics, collision callbacks, animation and frame updates must not advance authoritative ball/avatar state, decide hits or award points; those calculations remain on the Pi.

The Unity client consumes the existing bounded framed TCP `state_publication` subscription and uses the versioned control path for operator actions. Generate compatible C# message types from the canonical schema and test them against the accepted fixtures; existing Python/nanopb host checks do not prove C# interoperability. Receive and decode into bounded buffers outside scene updates, then apply validated snapshots to scene objects on the main thread. Most Unity APIs require the main thread; see [Unity thread-safety guidance](https://docs.unity.com/en-us/engine/6000.5/manual/scripting/optimization/programming-best-practices). Keep state queries and commits in the separate service, independent of Unity frames, garbage collection and rendering stalls. A stalled or disconnected Unity subscriber must not block that service; show stale state and recover through the existing session/subscription rules.

Use an explicit adapter from the contract's right-handed world to [Unity's left-handed coordinates](https://docs.unity.com/en-us/engine/6000.3/manual/working-with-gameobjects/gameobject-fundamentals/rotation-orientation/quaternion-and-euler-rotations-in-unity). Verify position, orientation and scale with known court axes and racket poses before integrating the cameras; do not copy quaternion components without a tested basis conversion. Preserve the wire values and [shared coordinate contract](coordinates-and-time.md#spatial-frames-and-calibration). Court-end changes affect team camera placement, not the world-to-Unity conversion.

## Lobby and fixed player identity

At startup the UI offers explicit team selection, then confirms the physical person, controller, playing hand and avatar according to [player assignment](player-assignment.md). Slots are fixed as `1 = A1`, `2 = A2`, `3 = B1`, `4 = B2`. Each slot represents one controller/person/avatar binding; the team is part of its identity, while front/back position is a court role that may change during play. Do not infer a new identity from whichever avatar is closest to the ball or whichever person crosses another in the camera view.

Use the existing association installation acknowledgement and resume barrier before marking a slot ready. A full doubles match starts only when all four assigned players are ready; do not insert an automatic AI substitute. One-through-four-controller capacity tests remain explicit diagnostic workloads rather than partially populated full matches. Show selected teams, slot labels, person/hand confirmation, connection/battery status and readiness faults in the lobby. Team changes or re-pairing use the versioned control procedure and retire old pending work/cues.

## Split views and avatar presentation

The renderer consumes bounded `state_publication` messages on a local subscription and may interpolate committed snapshots for a 60 Hz presentation target. It uses ordered event IDs `(game_session_id, writer_epoch, batch_id, event_index)` to avoid duplicate effects. It does not extrapolate a visual guess back into game authority. Keep recent events in the state-service history so skipped visual snapshots do not erase measurement provenance.

Render two simultaneous views of one committed world, one for team A and one for team B. Each camera is elevated and obliquely behind its own team's baseline, with its own team near and the opponents far. This is an angled behind-court perspective, not a strictly vertical overhead view. A horizontal split with team A above and team B below is a proposed layout; only two team-relative views are agreed. Both viewports use the same match version and presentation instant, even though their camera transforms differ.

Normal changes of court ends update the committed court-end state. Each camera then follows its own team's new side; team A/B identity, controller/person/avatar bindings and viewport ownership stay fixed. Camera transforms affect presentation only. They cannot rotate physical input into a different gameplay meaning, change world collision geometry or make a second copy of the simulation.

Avatar running and positioning follow Pi-calculated committed state. Human participants remain at their calibrated physical play stations; they do not need to run across the room to chase the virtual ball. Camera and IMU tracking remain active for body-local arm/racket motion, orientation, timing and swing/contact eligibility, following the shared gameplay/calibration contract. A separate pose display subscription may animate those gestures or diagnostics, but cannot overwrite the authoritative avatar root position or calculate a second hit. Mark stale/ambiguous observations visibly and preserve the Pi's failure/eligibility decisions. Constrained webcam geometry remains 2.5D; no guessed depth is presented as measured spatial tracking.

Interpolate only within bounded, event-consistent segments of committed motion. Split interpolation at racket contacts, bounces, net contacts, serve/point transitions and resets; do not smooth a ball through the net or court to conceal a discontinuity. Automatic avatar animation may follow committed movement, but animation cannot manufacture a reachable shot or feed a displayed collision back to physics. Both cameras display the same contact event and result.

## Player-facing UI and diagnostics

The player-facing display shows team/slot identities, normal `0/15/30/40/AD` point scoring with deuce/advantage, games and sets, tiebreak context when active, the server indicator and current serve attempt. Apply the canonical [rules](gameplay.md) from committed match state; do not infer points or service rotation independently in the UI. Show the selected server's controller-lift/toss phase and subsequent overhead-hit opportunity. The lift triggers a toss through physics; the overhead swing supplies the serve contact. A UI animation or operator button cannot silently bypass that gesture path in normal gameplay.

Keep required connection/battery/readiness, tracking/calibration faults and pause state visible. A proposed toggleable technical overlay can expose pose age/prediction horizon, clock-map uncertainty/status, game version/tick, simulation lag, queue occupancy, transaction/marker/event IDs, response/electrical populations, timeouts and trace gaps. Toggling detailed diagnostics must not hide essential gameplay fault indications or change runtime behavior. Missing diagnostic updates are shown as stale rather than fabricated healthy status. Trace/status subscriptions and UI work cannot block the state service.

UI pairing, team selection, pause, resume and reset use versioned control handling. Gameplay serve gestures enter through the normal tracked controller path; any deliberate diagnostic serve/reset command remains explicit and is executed by physics or a fresh fenced game session. The UI cannot directly mutate committed state, award a point or silently bind a controller to the nearest person.

## Presentation and integration evidence

Trace application update receipt, commit completion, render submission and, when available, actual presentation separately. Photodiode/display-patch experiments are needed to measure photons; neither snapshot commit nor a render call proves visible output. A game commit can be displayed after the controller timed out; keep that discrepancy visible instead of rewriting the controller outcome.

Implementation follows the [shared stages](project-stages.md): the accepted S0 contract supports the S1 headless state-store slice; the Unity two-view client is added within the later released integration/gameplay scope. Verify C# codec compatibility, the world-to-Unity coordinate adapter, atomic ball/avatar/serve/score changes, fixed roster identity through court-end and front/back-role changes, the four-player readiness barrier, gesture-driven serve phases and scoreboard transitions from canonical rule fixtures. Test that both viewports show the same match version/contact result and that interpolation does not cross collision/reset boundaries. Diagnostic one-through-four-controller tests do not establish a full four-player match.

Benchmark four-player batched state traffic while RTMO inference and both Unity views compete on the laptop, including a stalled/disconnected renderer and allocation-heavy UI work. Keep the existing 200 Hz controller stream, marker tracing and timing contracts unchanged; measure any added match-state/rendering cost. Require batch-service capacity and correct rejection/recovery before optimizing visuals. Real build/run commands, the verified Unity editor/build configuration and dependency locks must accompany source implementation; none exist yet.

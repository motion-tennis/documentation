# Troubleshooting

[Documentation home](../README.md) · [Master plan](master-plan.md) · [Development setup](development.md) · [Testing](testing.md)

## Current checkout

**Implemented:** documentation, shared specification artifacts, a documentation checker and the offline trace checker in `debug-units`. There is no running firmware, webcam/pose pipeline, physics service, game server, renderer or live collector. The reference profile is a specification, not an installed deployment. A failed attempt to run a guessed game/build command does not establish which dependency is missing. Follow [development setup](development.md) for the commands available now.

| Problem | Check and action |
| --- | --- |
| `python3` is unavailable or too old | The checker requires Python 3.9 or later. Use a compatible interpreter available on the development host; no third-party Python packages are required. |
| A relative documentation link fails | Confirm the target path and case, then compare the heading with its generated anchor. Update the source link or target together; run `python3 scripts/check_docs.py` again. |
| A project GitHub link is skipped | The linked component checkout is absent from the configured workspace. Clone the actual repository if available or use `--workspace` to point to the parent containing the checkouts. A skip is not remote-link verification. |
| A new GitHub documentation link returns 404 | Check whether the corresponding documentation commit has been reviewed and published. Local validation can resolve an uncommitted local file; it cannot make that file exist on GitHub. Access permissions may also hide a private repository. |
| A Mermaid block passes the checker but does not render | The checker only performs structural checks. Open the document in a Mermaid-capable viewer, obtain the parser error and correct the diagram. Record the viewer/version when investigating syntax differences. |
| A clone fails | Compare the remote with the central repository map and verify your GitHub access/SSH setup. Do not paste private keys or credentials into issue reports or documentation. |
| The offline trace checker rejects a file | Inspect its reported event/identity/time errors against the documented trace format. Do not erase failures or insert fabricated timestamps to make a hardware trace pass. Synthetic examples are marked as such. |
| The profile and a component document disagree | Use the current profile/schema version and [master plan](master-plan.md); update affected definitions together. Do not silently retain earlier Kinect-only, Linux-PC or TCP/JSON gameplay assumptions. |

## Proposed runtime diagnosis

The following table describes expected diagnostics for future implementations, not existing commands, logs or observed hardware behavior. Preserve the failing transaction's identifiers and timestamps before changing configuration. See [protocol](protocol.md), [physics](physics.md), [tracking](tracking.md) and [timing](timing.md) for the intended invariants.

| Symptom | Evidence to collect | Expected investigation or recovery |
| --- | --- | --- |
| Controller is connected but never completes a swing | Controller/session/request key, send time, Pi admission result, query/response and commit stages | A transport receipt is insufficient. Locate the missing application stage and terminate outstanding work at the configured deadline. |
| Every swing becomes a miss during occlusion | Frame quality, association version, selected joints, capture age and alignment uncertainty | Treat unavailable or unsuitable tracking as an explicit failure. Confirm no fallback maps tracking failure to a miss. |
| Webcam image exists but pose output does not | Actual camera mode, model/configuration, inference provider, input tensor and worker errors | Capture is not pose inference. Verify the selected Windows stack, supported model artifact and four-person worker before enabling play. See [tracking stack](tracking-stack.md). |
| Tracking is unexpectedly slow on the RTX laptop | GPU model/VRAM, driver, ONNX Runtime provider, model hash, inference/transfer time and CPU/GPU load | Verify GPU execution rather than a silent CPU fallback. Benchmark four people with rendering active; reduce load through a named profile revision, not an undocumented rate change. |
| All four players do not fit or hands blur | Actual webcam generation, lens/FOV, focus range, exposure, lighting, placement and sample frames | Verify whole-body focus and required hand visibility at the real play distance. A high output resolution or advertised 60 fps does not establish usable pose input or low acquisition delay. |
| Racket attaches to the wrong player | Controller boot/session, tracking session, person ID, association history | Invalidate ambiguous association and repeat deliberate pairing. Do not infer identity from reused numerical person IDs after a tracking restart. |
| Motion appears mirrored, rotated or scaled | Calibration ID, source/destination frames, units and quaternion ordering | Verify transforms using known reference positions and rotations. Follow [coordinates and time](coordinates-and-time.md); do not repair the view while leaving collision coordinates inconsistent. |
| Raised hands appear at the wrong depth or a swing misses outside its lane | Calibrated interaction plane, pixel rays, playing lane and physical reference positions | The initial webcam mode is constrained 2.5D. A floor homography is not a metric hand-depth measurement. Reject unsupported geometry or add a separately validated depth/multiview stage. |
| Ball jumps backwards or hits disappear | Game session, query ID, base and committed versions, update ID, arbitration order | Reject stale updates. Ensure game owns committed state and physics alone calculates its advances; rendering must not independently commit movement. |
| Only some inputs in a batch have outcomes | Batch/query entries, ordered event indices, per-controller IDs and atomic commit result | A batch must preserve every admitted measurement. Never apply half an update or use one controller's result for another. Count missing entries, reject invalid batches and let delivery failures terminate locally. |
| State service seems healthy but simulation repeatedly pauses | Query/commit RTT, last resolved batch, retry times, scheduler release and simulation lag | The 5 ms cadence depends on PC replies. One ambiguous commit pauses the writer at 8 ms; lag above 20 ms also pauses. Locate blocking or contention rather than spawning competing writers. |
| Ball stops while controllers are idle | Physics scheduler tick log, network waits, game commit readiness | Check periodic jobs as well as event transactions. Network waits must not create an unlimited tick backlog; apply the documented pause/degradation policy. |
| Controller vibrates twice for one hit | Feedback/event ID, duplicate and retry history, controller terminal record | Deduplicate before actuation; reconcile lost commit responses before repeating a state update. Retransmission must not create a new event. |
| Controller actuates after a reboot or very late | Original and current session IDs, request deadline, response arrival | Discard and count obsolete-session or terminal-transaction responses. Start a new boot/session identity after restart. |
| Controller is powered but cannot join the WLAN | Exact ESP32 variant, SSID band/channel, association status, local credentials and selected network variant | The ESP32-S3 reference uses 2.4 GHz. Check external AP baseline A or Pi hotspot B, its actual AP mode and configured endpoint. In B also verify wired-laptop and Windows collector routes; a Pi reply alone does not prove debug reachability. |
| Wireless response has periodic long delays | Modem-sleep configuration, AP/channel load, radio coexistence, RSSI and query/feedback traces | Verify modem sleep is disabled through the pinned Zephyr ESP32 driver configuration and Bluetooth is unused; measure power/runtime consequences. Separate radio delay from the mandatory PC state exchanges. |
| Pi performance degrades during a long run | Pi 3 B model/kernel, thermal/throttling and undervoltage indications, CPU load and storage activity | Use the hardware power/cooling plan; keep inference and renderer off the Pi and disk/log exports out of the measured path. Recheck batch-service capacity under sustained load. |
| LED or motor behavior differs from the intended feedback | Feedback parameters, output marker, measured pin/driver output and physical onset | Separate requested intensity, electrical actuation and physical vibration. Verify selected wiring and driver before attributing delay to the network. |
| Software RTT looks good but physical feedback is late | `t0`, `tr`, `t1`, logic-analyzer trace, optional photodiode or vibration measurement | Report application response, electrical feedback and physical onset separately. Check scheduling, driver and sensor boundaries. |
| Negative data age or implausibly small one-way delay | Pi reference epoch, source sessions/clocks, mapping version, offset/drift, age-dependent uncertainty and restart logs | Inspect the viewer's numeric bounds and uncertainty bands. Overlapping intervals may leave order unresolved; missing/invalid maps require separate local lanes and no cross-device duration claim. Preserve valid historical mappings and re-establish future mappings; do not substitute the latest fit or half the RTT. |
| Recent packet contains an old pose | Original capture timestamp, processing completion and arrival time | Base freshness on capture time with valid mapping and uncertainty. Arrival recency does not make a stale frame suitable. |
| Pose and IMU always look misaligned despite low network RTT | Camera timestamp semantics, delayed pose time, historical IMU buffer and mapping uncertainty | Align the pose to historical IMU observations, then replay orientation to evaluation time. Comparing every pose only with the newest sample confuses acquisition delay with a clock error. |
| Latency rises when logging is enabled | Queue occupancy, log overflow, CPU use, serial/storage write durations | Buffer logs and export asynchronously. Quantify observer overhead; count loss rather than blocking the measured path indefinitely. |
| Collector loses events while gameplay continues | Per-component emitted/dropped counters, trace sequence gaps, socket/buffer occupancy and capture drops | This is valid isolation behavior but invalid evidence for a complete-accounting acceptance run. Preserve loss counters, fix collection capacity and repeat the affected trial. |
| Percentiles improve while users see more failures | All admitted/started transaction counts, failure/timeout/dropped counts, filtering policy | Include failure responses and censored observations in the report. Successful-only latency can hide overload. |

## Useful issue report

Provide the affected component, all relevant repository revisions, profile/schema hashes, hardware/OS/kernel and GPU/provider versions, steps to reproduce, expected versus observed outcome, run ID, correlation/query/batch keys, sanitized configuration and a bounded log/trace extract. Include clock domains, timestamp uncertainty and actual measurement boundaries. Do not include Wi-Fi passwords, tokens, private keys or unnecessarily identifiable camera recordings. State whether the evidence came from live hardware, synthetic trace data, replay, a simulator or static documentation review.

## Transport and connection setup

Use one serialized `motion.v03.Envelope` per message. Controller input/feedback and pose/frame-status use UDP, at most **1,200 bytes including the envelope**. Reject oversized packets before processing. A skeleton packet contains one person, not all four people; a separate frame-status packet lists visible IDs.

The required Pi/PC `ball_state_request`, `ball_state_response`, `state_update` and `state_commit_result` use a **dedicated TCP state connection on port 41010**, initiated by the Pi. Each message has a four-byte big-endian length followed by exactly one envelope, at most **8,192 envelope bytes**. Local `state_publication` subscriptions use the same frame limit. This explicitly versioned transport change keeps eight decisions and a complete match in one atomic message. No state message is sent as an oversized UDP datagram. It changes neither controller sampling nor the required query/response path. The codec size evidence and new bounds are recorded in [S0 evidence](s0-baseline.md).

Control remains a separate TCP connection: the same four-byte framing, a maximum 65,536-byte outer frame and a 1 s assembly deadline. Typed body bounds are tighter (including at most 4,096 configuration JSON bytes); the outer limit does not authorize unbounded allocation. Control handles hello, association, clock exchange, readiness, pause/reset, calibration/configuration transfer, match setup and uncertain-commit lookup. A blocked state stream must not block recovery control. Live data does not wait for log collection or a UI frame.

Reject zero/oversized frame lengths before allocation and reject a body on the wrong channel. The state stream has at most three outbound frames (original plus two exact retries), one inbound assembly buffer, one state batch in flight and an 8 ms partial-frame deadline. A partial-frame timeout or malformed frame closes that connection; never attempt to resynchronize by scanning payload bytes. Do not enqueue another retry when an identical copy is still unsent. Nonblocking I/O and bounded queues preserve the existing 5 ms query, 8 ms ambiguity and 50 ms controller deadlines; TCP retransmission or local write completion never extends them or proves acceptance. Queue exhaustion is an explicit overload/pause outcome. First register the writer over control. Every new state connection then starts with `hello`/`hello_result` using the same registered sender/session and exact hashes; only physics/game roles are allowed. This attachment returns the already assigned game session/epoch and cannot allocate a new epoch. Reject an unregistered/superseded writer, invalidate its previous state socket, and require the Pi to compare the returned session/epoch with its control registration. Reconnect uses the same attachment and fencing; resolve uncertain commits through control before new work. TCP latency and head-of-line blocking require S2/S5 measurement.

Use the selected WLAN variant's AP with a controller-compatible authenticated mode and isolated test network: external AP baseline A or planned Pi hotspot B. Bind sender role, ID, session and UDP source endpoint during setup; repeat registration after topology changes and reject unknown senders. This is not cryptographic message authentication. Public/untrusted network use requires a separately reviewed authenticated/encrypted profile; keep credentials outside Git.

## Envelope, versioning and scalar validation

Set `major=0`, `minor=3`. Reject 0.2 peers at setup; no mixed-version fallback or reinterpretation of old ball-only fields is allowed. Require exact supported profile/schema hashes during `hello`; unknown versions, fields with incompatible semantics, unbound sessions or invalid message roles fail setup. `sender_id` is a provisioned numeric node ID, never a person identity. `sender_session_id` and `run_id` are exactly 16-byte unique IDs. `message_seq` increases within the sender session; identical retries reuse identity and payload. `sent_time_us` belongs to that sender session's `clock_id`.

Counters and timestamps use protobuf `uint64`, with a mandatory wire-value maximum of **2^56 - 1 = 72057594037927935** so every varint fits in eight bytes. Validate this semantic limit in every codec; change the applicable session before reaching it. Full-width uint64 extremes are not legal profile values. This bounds codec fixtures but does not by itself prove that a message fits its transport cap. JSON trace exports use decimal strings to avoid floating-point precision loss. Never reuse a session after process restart or wrap counters into an outstanding key. Hashes are 32 bytes. Physical values must be finite. Proto3 default/absent values are not automatically valid: required nested messages, nonzero IDs, correct UUID lengths, enums other than UNSPECIFIED, vector completeness and bounds must be checked by handlers. An unavailable timestamp has `timing_valid=false`, not a fabricated capture at zero.

Limits: four active controllers/player slots; up to eight query/decision entries, at most two per controller; exactly 17 unique COCO joint indices per tracked-person message; reasons at most 128 UTF-8 bytes. All Protobuf strings must contain valid UTF-8 and no embedded U+0000, matching the statically bounded C codec representation. Indices 0–16 are nose, left/right eye, left/right ear, left/right shoulder, left/right elbow, left/right wrist, left/right hip, left/right knee, left/right ankle. Missing joints use `UNAVAILABLE`; zero coordinates are not a missing-data sentinel. Keypoint score and normalized image coordinates are in [0,1]; out-of-frame joints are marked unavailable, not clipped into apparently valid positions. Decoder collection lengths and memory must be bounded before allocation. Full-match bounds are four bindings/avatars, four service/receiving-order entries, at most five completed sets and sixteen rule events per batch. Role names are at most 16 UTF-8 bytes. The exact-hash v0.3 profile accepts only canonical known-field envelope bytes: ascending field-number serialization, shortest scalar encoding, the generated packed repeated-scalar representation and no duplicate singular/unknown fields. Compare received bytes with canonical re-encoding (or use an equivalent strict raw-wire validator) before semantic acceptance. This detects embedded NUL loss in a C string buffer as well as ambiguous alternate encodings; checking decoded strings alone is insufficient. Generated static C codec bounds and their measured host sizes are checked by the [contract suite](s0-baseline.md#reproduce-the-contract-evidence).

## Units and coordinate semantics

Use SI: metres, seconds for physics, m/s, m/s², rad/s. Wire time is integer microseconds; haptic duration is integer milliseconds. Controller `specific_force_m_s2` includes gravity as measured in the calibrated sensor frame; physics owns gravity handling. No quaternion is required from the controller. Internal quaternion convention remains normalized `[x,y,z,w]`, active local-to-world rotation; q and -q are equivalent.

World is right-handed, origin court center, +X court-right from near baseline, +Y up, +Z toward near baseline. `Ball` always uses that world frame and the named calibration. Webcam joints are normalized coordinates of the original undistorted image after reversing model resize/letterbox transforms. They are not metric 3D coordinates. Physics applies the versioned `plane_2_5d` calibration. The outgoing velocity vector defines speed and angles; derive elevation `atan2(vy,sqrt(vx²+vz²))` and azimuth `atan2(vx,vz)`. Undefined zero-vector angles remain unavailable.

## Message contracts and correlation

| Message | Required semantics |
| --- | --- |
| `controller_input` | One transaction per regular IMU sampling boundary: `(controller_id, session_id, request_seq)`, `t0_us`, current `sample_id`, capture metadata/raw sensor ticks, association/calibration, specific force, angular rate, saturation, battery voltage. Envelope session must match transaction session. No silent sample decimation. |
| `skeleton_frame` | One person per datagram: common capture `frame_id`, tracker-session-scoped `person_id`, original capture/time kind/uncertainty, processing completion and clock, image dimensions, calibration and 17 joints. Capture may be unknown; bounded-freshness gameplay must then remain unavailable. |
| `frame_status` | Same tracker session/frame ID, observed person IDs, readiness and cumulative skipped-frame count; empty IDs explicitly means no person. Missing status/pose packets also expire through freshness limits. |
| `ball_state_request` | `game_session_id`, writer epoch, batch ID, ordered query entries containing a unique query ID and the full controller transaction key. Every valid selected input has its own logical query. Empty entries mean periodic-only work. |
| `ball_state_response` | Echo exactly top-level game session, writer epoch, batch and query entries even on rejection; return one atomic snapshot with game session, version, tick, tick duration and complete `MatchState`, or explicit rejection. Match game session/epoch/batch/entries, including periodic-only empty-query batches, so a delayed pre-restart response cannot match a new writer. No cached push replaces this required response. A retry of the same query within its lifetime returns the same retained response. |
| `state_update` | Same game session, writer epoch and batch ID; exact base version, target tick, complete final `MatchState`, tracking session, ordered decisions and separate rule events. Commit entries may contain only `HIT` or `MISS`; invalid/stale/error inputs receive direct failed feedback and cannot be committed as normal decisions. Each decision retains its transaction, current sample, selected frame/person, association, source capture times, outcome, swing/cue and event index. Full source clocks, historical sample references and uncertainty are preserved in the trace. |
| `state_commit_result` | Echo game/session/epoch/batch; acceptance returns original committed version/tick, rejection reports reason. Acceptance is atomic for the full candidate state and ordered event list. |
| `feedback_result` | Exact originating transaction, outcome and cue; `committed=true` plus game/epoch/batch/event-index/version/tick for hit/miss. Errors have `committed=false`; commit identity fields are unavailable and must not be interpreted as version zero. |
| `state_publication` | Complete committed match snapshot, ordered decisions and separate rule-event list for the local renderer/debug consumers. Must not make the renderer an authoritative writer. Delivery uses a bounded local TCP subscription; delayed frames may be skipped while event IDs remain deduplicated. |

Outcome enum names in the schema are uppercase; human trace names use their lowercase spelling: `hit`, `miss`, `invalid_input`, `tracking_unavailable`, `stale_input`, `state_conflict`, `timeout`, `overloaded`, `internal_error`. A valid no-collision sample is a miss even if it is not eligible for a physical miss cue. A sensor/communication failure is never a miss.

The durable gameplay event key is `(game_session_id, writer_epoch, batch_id, event_index)`. Decisions occupy contiguous indices 0..7; rule events occupy contiguous indices 8..23, starting at 8 even in periodic-only batches. Their namespaces never collide. Rule events optionally name a decision cause; absent causes never create artificial transactions. The rule-event list records chronological rule transitions; its index offset is an identity convention, not a claim that all rule transitions occur after all decisions. The update key is `(game_session_id, writer_epoch, batch_id)`. A physics restart receives a new epoch; these keys cannot collide just because a sequence resets. `swing_id` and `cue_id` are scoped to the physics writer epoch and controller association. Input/feedback deduplication always uses the controller transaction key, not event proximity in time.

## Diagnostic threshold markers

The [independent threshold marker](imu-trigger-markers.md) adds only diagnostic trace records. `motion.proto`, gameplay payloads, per-sample transaction semantics, rates and expiry stay unchanged. An asynchronous marker-to-transaction link lets the debug tools join the existing query, batch, commit and feedback identities. The marker is not carried in a new gameplay message, is not a new transaction, and cannot alter admission or priority. Packet capture needs the separate trace evidence to identify marked samples.

## Batched query and atomic commit example

This is an illustrative logical transcript, not serialized JSON or a captured run:

```text
batch 81, writer epoch 3
  query 901 -> controller A / boot A7 / request 120
  query 902 -> controller B / boot B4 / request 225
ball_state_response(batch 81, queries [901,902], version 17, tick 240)
  event 0 evaluates A against version 17 -> candidate A
  event 1 evaluates B against candidate A -> candidate B
state_update(batch 81, base 17, target tick 241, final candidate B, events [0,1])
state_commit_result(batch 81, accepted, committed version 18, tick 241)
feedback A/request120 -> committed18/event0
feedback B/request225 -> committed18/event1
```

Intermediate candidates are not separately committed versions. Both decisions record common base 17 and their event order. All admitted query entries must appear in the decisions or be explicitly rejected before submission; no controller ID may disappear from accounting. If validation changes during computation, rebuild the candidate deterministically without invalid entries and return their explicit errors; never keep later calculations based on a removed earlier hit. Unknown partial acceptance is forbidden.

## Matching, bounds, and expiry

The [profile](../spec/reference-profile.json) is authoritative for proposed numeric settings. Controller pending capacity is 16 (80 ms at 200 Hz, greater than the 50 ms expiry); Pi admission is four per controller; batch maximum eight with at most two per controller; one state batch in flight; retained IMU history 256/controller and poses eight/person. These queues serve different purposes and must not be conflated.

Controller inputs are sent once, with no live application retransmission. Missing data becomes a timeout or a gap; UDP checksum success or Wi-Fi MAC acknowledgement is not an application result. The Pi caches terminal results for duplicate requests while retained. The controller never actuates a duplicate or expired feedback result.

Ball query retries once after 2 ms, expires after 5 ms. Commit resends the exact original payload after 2 and 4 ms; after 8 ms without resolution, pause the writer and use control-plane status recovery. Do not start a new state batch while the commit is uncertain. Every stage retains the same local deadlines; retries never extend the controller's 50 ms expiry. Query expiry/ambiguity timers are local durations, not unsynchronized remote deadlines.

Retain query/commit deduplication records for 2 s and up to 512 batches; at 200 batches/s this covers 400 batches plus headroom. If full before time retention expires, reject/pause new state work rather than evict an outcome needed for recovery. A status lookup after expiry returns UNKNOWN_BATCH; it does not prove the update was never committed. Recover/reset the game session before resuming if the outcome cannot be established. A current match snapshot alone cannot answer whether a particular event committed. Retain both query/commit payload identities as well as their results: reusing a batch key with different bytes is invalid, never an idempotent retry. Process a retained identical duplicate before checking its now-stale base version so the original accepted result is returned without applying it twice.

## Control operations and lifecycle

`hello` announces role (`controller`, `physics`, `tracking`, `game`, `debug`, `renderer`), profile/schema hashes and receive endpoint; `hello_result` accepts explicitly. Every new process session repeats readiness and clock setup. A reconnect of the same physics session may resume its epoch only if the game confirms it has not admitted a replacement writer; the old transport is invalidated. New physics sessions fence old epochs.

`Association` binds one controller session to one tracker-session/person, playing hand, slot and calibration; its transaction's sequence is zero because this control record identifies a controller, not a measurement. Increment association version on every change. Physics first suspends the old binding and explicitly rejects old queued work. Send an installation with `command_id`; the controller installs it while suspended and returns the same association/command with `response=true` and `accepted=true`, or an explicit rejection. Only after matching acceptance and valid clocks/calibration does physics send a correlated `resume` command. Until that barrier completes, no normal gameplay input is eligible. Retry installation idempotently by command ID; TCP delivery alone is not installation acceptance. Tracking restart, player ambiguity or re-pairing repeats this barrier. No automatic reassignment to a nearby person is permitted.

During that barrier, the controller retires all pending records and cancels queued cues tied to the old association/calibration, retaining their failure reasons. Every pending entry stores the association/calibration used at transmission; a matching late transaction is still ineligible if that binding has changed. Physics resolves or explicitly invalidates old in-flight batches before resuming the new mapping. Feedback without a live pending entry cannot actuate, even if its controller boot session has not changed.

Allowed `ControlCommand.operation` values are `configure`, `ready`, `pause`, `resume`, `reset_session`, `commit_status`, `subscribe_state`, `run_start`, `run_stop`. Every command has a unique command ID and matching result. Configuration is a versioned UTF-8 JSON object containing profile hash, endpoint map, calibration transform/rules and limit overrides; validate against the published profile and calibration requirements before accepting. `commit_status` identifies game/epoch/batch and returns its cached `state_commit_result`, or UNKNOWN_BATCH. `pause` admits no new gameplay work; `reset_session` invalidates old snapshots and pending batches; neither directly creates competing physics updates.

## Pi-reference clock exchange and mapping ownership

The Pi owns runtime mapping and clock-dependent readiness. It maps each source monotonic domain with `T_pi = a * t_source + b`, retaining both offset and rate correction. Native timestamps remain unchanged. Mapping versions are immutable and scoped to source ID/session/clock plus Pi reference session/clock. Tracking/game/renderer may share a verified host-clock fit and evidence, but each producer session receives its own bound mapping record/ID; distinct clock domains and an independent camera clock need separate conversion evidence. See [clock definitions, estimator requirements and uncertainty](coordinates-and-time.md#pi-reference-clock-mapping).

The proposed implementation default is to initiate exchanges from the Pi over each existing bidirectional control connection. An ESP32 can establish its registration connection to the Pi and still answer a Pi-originated exchange on that same socket; no new listener is needed. The Pi uses existing game/tracking control connections for the relevant laptop domains. Each exchange is correlated with its initiator session and `exchange_id`, and the response must come from the expected registered peer session.

| Boundary | Clock | Existing field or evidence |
| --- | --- | --- |
| `A`: request send | Pi reference | `ClockExchange.source_send_us`; retained locally and echoed in the response |
| `B`: complete request receipt | Peer source | `receiver_receive_us` in the response |
| `C`: response send | Peer source | `receiver_send_us` in the response |
| `D`: complete response receipt | Pi reference | Recorded locally by the Pi; retained with `A`, `B` and `C` in exchange evidence |

The request has `response=false`; its receiver times are not yet available. The matched reply has `response=true` and echoes the request identity/time with the peer's two times. Envelope sender identity/session/clock still describes the actual sender; `source_send_us` describes the exchange initiator even when the peer sends the reply. Capture send timestamps close to the framed-message I/O boundary and receipt timestamps at complete-frame reception, keeping later validation/handling boundaries separate. Timestamp placement, buffering and TCP retransmission affect the observation and must appear in uncertainty and rejection evidence.

Preserve all four raw times and both clock/session identities. Source-initiated diagnostic exchanges are also possible with the same message, but their fourth timestamp is local to that initiator and must be retained/exported before claiming a complete observation. No three-timestamp transcript may be treated as a full exchange. With Pi initiation and equal-rate approximation, the peer-minus-Pi offset is `((B-A) + (C-D))/2`, so conversion to Pi time subtracts that estimate; the maintained model additionally fits drift. [RFC 5905, section 8](https://www.rfc-editor.org/rfc/rfc5905.html#section-8) describes the four-timestamp offset/delay formulation. Neither that estimate nor a low-delay exchange proves symmetric paths, and one-way delay must never be reported as RTT/2.

Filter high-queue/outlier observations and fit offset/drift robustly over recorded observations. Concrete fit windows, counts and weighting remain implementation choices, not additional fixed profile values. Export the Pi's immutable mapping versions and raw exchange evidence asynchronously through the debug path, including anchors, offset/rate and drift ppm, fit window, validity interval, last refresh/age, state/reason and time-dependent uncertainty bounds. The manifest's `clock_maps` registry resolves `details.clock_mapping_id` for a single-source conversion. Pi-issued mapping-use evidence or multi-source `details.clock_mapping_refs` entries bind each original event/sample/time to the version used by the runtime; missing versions or assignments remain unresolved. Raw ESP/laptop emitters never wait for a map or overwrite native timestamps. Signed/fractional fit parameters remain metadata, separate from unsigned raw timestamps. Debug consumes those exact versions; neither the collector nor viewer participates synchronously in clock readiness or gameplay. The [trace contract](https://github.com/motion-tennis/debug-units/blob/main/docs/trace-format.md) defines the evidence destination; its mapping validation remains planned.

The existing candidate settings remain 1 s refresh, 5 s maximum age and at most 2 ms network mapping uncertainty per source. The accuracy gate requires a justified error bound; an offset estimate, fit residual or unknown bound is insufficient. Rate uncertainty grows the bound with age; expiry or excessive uncertainty invalidates readiness even if the control connection is alive. Different-source comparisons conservatively include both mapping bounds plus event/capture error, so two sources at 2 ms each permit 4 ms mapping uncertainty before those additional terms. Same-clock/session elapsed times need no mapping.

The asynchronous mapping export also includes authoritative source-time selection intervals for trace-only events not converted during runtime processing. The viewer can use them for explicitly labeled display conversions; they never replace missing expected runtime-use evidence. Keep selection history, full source/reference bindings and validity boundaries. This allows diagnostic marker/render timestamps to be displayed without adding a synchronous debug-to-physics round trip; see the [clock contract](coordinates-and-time.md#pi-reference-clock-mapping).

A Pi restart/reference discontinuity starts a new reference epoch and prevents future reuse of live mappings to the old reference. Source reboot/session change prevents future reuse of that source's mapping. Evaluate validity at the event's source-time interval and epoch; later expiry/reboot does not invalidate earlier history that used a valid mapping. Retain historical versions without silently refitting old events. Events without a mapping valid for their time retain causal IDs and separate local-clock debug lanes, with no cross-source duration claim. Required gameplay freshness/alignment gates fail closed, while the continuous 200 Hz stream, per-sample identities, local deadlines and explicit outcome accounting remain unchanged.

## Doubles match contract extension

**Implemented contract source and offline validation; S0-accepted interface design.** The v0.3 schema carries typed match configuration, full snapshots/candidates and rule events. Its generated host codecs and semantic fixtures are described in [S0 evidence](s0-baseline.md). This is not a running doubles game or target-device interoperability claim.

### Setup and immutable configuration

`MatchSetup` travels over control and carries a command ID, game session, current writer epoch, `MatchConfiguration`, SHA-256 and explicit response/acceptance. Configuration contains positive roster/rules revisions, exactly four `PlayerBinding` entries in slot order 1..4 and `MatchRules`. Slots 1/2 mean A1/A2 and 3/4 mean B1/B2; teams never depend on current court ends. Each binding includes controller ID/boot session, tracker session/person, avatar ID, hand, physical station, association version and calibration. Controller IDs, avatar IDs, stations and tracker-session/person keys are unique. All four bindings use the one active tracker session. A slot binds a persistent human/avatar identity, not a front/back role.

The configuration hash covers deterministic `MatchConfiguration` Protobuf bytes: known fields only, ascending field-number serialization, canonical scalar encoding and slot-sorted players; no maps or unknown-field extension bags. Match setup compares hashes and semantic fields, not arbitrary incoming serialization order. The suite compares generated Python and C encoding. Setup is fenced by the registered physics session and current writer epoch. Repeated accepted command IDs must carry the same configuration; changed payloads are rejected. A lost setup ACK is recovered by retrying the identical command and comparing the retained accepted digest; it never permits a second installation or a stale writer. The immutable tuning hash names a separately versioned calibration/movement/gesture parameter artifact; S0 fixtures use an explicitly synthetic hash, not a claim of measured tuning.

Setup is accepted only while suspended, after all four existing association installation ACKs match the configuration. It does not itself activate play: the existing clock/calibration/readiness and correlated resume barriers remain required. All participants retain the accepted configuration by game session, revisions and hash. Query responses, candidates and publications reference exactly that configuration. A new roster revision for the same confirmed human after controller/tracker restart requires paused reconciliation, reinstallation and renewed acknowledgement; a real player/team substitution requires a new game session. Rules/tuning changes also require a new session. No queued old-revision candidate may cross that barrier.

The proposed supported rule family is standard advantage games, sets to six with a two-game lead and a seven-point/two-point-lead tie-break at six-all, including the final set. `sets_to_win` may be 1, 2 or 3; default 2 remains a versioned assumption for review. At most five completed sets are representable. A configuration may not silently substitute no-ad scoring or an advantage final set. New rule families require a profile revision.

### Complete state and events

| Contract area | v0.3 fields and invariant |
| --- | --- |
| Configuration reference | `MatchState.roster_revision`, `rules_revision`, `configuration_sha256` resolve to the accepted immutable setup. No team data is added to each IMU sample. |
| Ball and avatars | `MatchState.ball`; exactly four slot-ordered avatars with world root, velocity, heading, automatic target, movement mode and teammate coverage owner. All physical values are finite. Coverage owner is zero (unassigned) or a same-team slot. |
| Serve and receiving order | Phase, assigned server/receiver, deuce/ad side, attempt 1/2, toss identity, attempted-stroke and net flags; service order is a four-slot permutation alternating teams, receiving order is A-deuce/A-ad/B-deuce/B-ad. Orders are fixed within each set; a new set can choose valid new orders. The tie-break retains its first server. |
| Rally and point | Rally/contact/bounce identities, last hitter, bounce side/count, net status, pending first service return, same-return contact slot mask and optional point winner. A zero hitter/identity means no such event yet; it is not a fabricated observation. |
| Score | Canonical love/15/30/40/advantage, active games/sets, tie-break flag/points and ordered completed sets. Two simultaneous advantages are invalid. At match completion the winner and completed-set counts agree. Counter exhaustion pauses with a technical error before overflow; never truncate an unusually long tie-break. |
| Lifecycle/time | Match ready/playing/paused/finished, winning team, monotone point identity, Pi-reference state time and exact reference session/clock. Source timestamps and mapping provenance stay in the diagnostic records. |
| Rule events | At most sixteen typed events for toss/cancellation, attempt, contact/bounce/out, fault/let, point/game/set/match, ends and technical pause/resume; explicit point, tick, player/team, serve attempt and optional decision cause. Durable identities use the accepted commit key plus rule index 8..23. |

`Snapshot.match` replaces the reserved old ball field; `StateUpdate.match` replaces its old ball field. The Pi calculates one full candidate. The PC accepts or rejects ball, four avatars, serve/rally, score, configuration references, decisions and rule events together against one base version and writer epoch. Publication carries that same snapshot and event set. It must not recompute rules or invent a second authoritative state.

A periodic-only batch still queries a full snapshot and may advance motion, serve/rally or score with rule events and zero decisions. A normal per-sample `MISS` cannot by itself award a point. A cancelled toss is distinct from an attempted missed strike; a let preserves the previous serve attempt. Technical failures preserve committed score and pause eligibility rather than becoming sporting faults. These distinctions are represented by contract fixtures; calculating tennis rules and recognizing gestures are S4 implementation work.

Reject a candidate with stale configuration/base version, wrong session/epoch, invalid ordering, duplicated identity, missing required state, nonfinite value or an out-of-bound collection. If a previously selected input is removed after freshness revalidation, rebuild all later candidates from the queried base and account explicitly for the removed input; do not retain downstream effects of a removed hit. Exceeding sixteen rule events is a visible overload/pause, never a truncated accepted commit.

Local rollback also covers fusion/contact latches, gesture/swing completion and pending cue decisions. Those private histories are not represented as complete restartable state in this wire snapshot. A new Pi writer epoch starts suspended, queries committed state and reconciles or resets private histories with an explicit point resume/replay decision before readiness. It must not continue an interrupted rally using guessed latches. Identical retries return the original result; changed payloads under the same key are invalid, and an expired unknown commit requires session recovery.

The four 200 Hz IMU streams, independent markers, clock-map semantics and existing timing targets remain unchanged. See [ADR 0011](adr/0011-full-match-contract-and-state-stream.md) for the bounded state-stream decision and [component reviews](s0-baseline.md#component-reviews-and-s1-handoffs) for implementation dependencies.

## Error and lifecycle behavior

Return one correlated terminal result for every parseable admitted measurement, including misses and invalid inputs. For a malformed request without recoverable identity, count the receiver failure; the controller's own pending key expires locally. Log every input not admitted, dropped log record, expired query, late/duplicate/unmatched response and suppressed cue. Retain the original local terminal outcome even when a later commit is discovered; do not fabricate a second completion.

`Cue.electrical_eligible=false` and `CUE_NONE` mean no per-transaction actuation is expected. Continuous status LED state is not an electrical pulse for every sample. Eligible cues are bounded semantic hits or completed missed swings; fault behavior is distinct. Normalize requested intensity to [0,1], cap it by characterized driver limits, and measure actual drive onset separately.

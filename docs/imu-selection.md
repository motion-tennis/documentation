# Prototype IMU decision and later alternatives

[Documentation home](../README.md) · [Marker contract](imu-trigger-markers.md) · [Hardware](hardware.md) · [Controller](controller.md) · [Open decisions](roadmap.md)

Decision date: 2026-10-25. **Agreed design:** use **MPU-6050 over I²C with Zephyr for the first prototype**, preserve the continuous 200 Hz stream, and develop the independent hardware marker without gating gameplay transmission. The user's reported MPU-6050 availability supports starting with this device. **Open:** measured marker feasibility and final production hardware. **Implemented:** documentation and source review only; no firmware, hardware or driver integration was tested. See [ADR 0008](adr/0008-mpu6050-zephyr-prototype.md).

The [reference profile](../spec/reference-profile.json) records this prototype selection as `webcam-pi3-wireless-v2`. BMI270 and ESP-IDF are historical choices superseded for this prototype. Rates, limits, timing targets, ports and the gameplay schema remain unchanged. The checks below validate the selected prototype; they do not reopen its IMU/runtime choice by default. LSM6DSV16X/32X remain later alternatives if measured constraints require another sensor.

For DSV16X, ST specifies absolute wake-up through the low-pass/user-offset path with both `SLOPE_FDS` and `USR_OFF_ON_WU` enabled. The comparison applies to positive and negative per-axis values, not a computed vector magnitude or gravity-free world acceleration. Threshold resolution is selectable from 7.8125 to 250 mg with a six-bit value; the largest setting is 15.75 g. Duration increments follow `1/ODR_XL`: 5 ms at 200 Hz. Filter delay, evaluation phase, duration and IRQ handling remain separate latency contributions. [ST AN5763, section 5.3](https://www.st.com/resource/en/application_note/an5763-lsm6dsv16x-6axis-imu-with-embedded-sensor-fusion-ai-qvar-for-highend-applications-stmicroelectronics.pdf).

## What Zephyr support establishes

An MCU board target, an IMU devicetree binding, a sensor driver and support for a particular trigger are separate requirements. A generic API enum does not establish device support: Zephyr distinguishes delta/motion triggers from threshold-crossing triggers. [Zephyr sensor API](https://github.com/zephyrproject-rtos/zephyr/blob/main/include/zephyr/drivers/sensor.h).

Both [DSV16X](https://docs.zephyrproject.org/latest/build/dts/api/bindings/sensor/st,lsm6dsv16x-spi.html) and [DSV32X](https://docs.zephyrproject.org/latest/build/dts/api/bindings/sensor/st,lsm6dsv32x-spi.html) have upstream bindings and share the DSV16X driver. Its [configuration implementation](https://github.com/zephyrproject-rtos/zephyr/blob/main/drivers/sensor/st/lsm6dsv16x/lsm6dsv16x.c) handles `SENSOR_ATTR_SLOPE_TH` and `SENSOR_ATTR_SLOPE_DUR`; duration is a register code capped at three, not an arbitrary millisecond value. Its [trigger implementation](https://github.com/zephyrproject-rtos/zephyr/blob/main/drivers/sensor/st/lsm6dsv16x/lsm6dsv16x_trigger.c) supports data-ready and wake-up through `SENSOR_TRIG_DELTA`. This does not automatically configure the absolute low-pass mode. Both interrupt sources use the same selected `drdy_pin`, and application handlers run after deferred interrupt processing. Separate routing and trustworthy edge timestamps therefore require reviewed integration work.

The [LSM6DSO trigger code](https://github.com/zephyrproject-rtos/zephyr/blob/main/drivers/sensor/st/lsm6dso/lsm6dso_trigger.c) exposes data-ready, tilt and tap, without a wake-up/threshold handler. The [BMI270 binding](https://docs.zephyrproject.org/latest/build/dts/api/bindings/sensor/bosch,bmi270-spi.html) and [trigger code](https://github.com/zephyrproject-rtos/zephyr/blob/main/drivers/sensor/bosch/bmi270/bmi270_trigger.c) provide data-ready/motion infrastructure, but the selected feature image and enabled interrupt support still need verification; any-motion semantics do not become absolute acceleration through API naming.

Reviewed sources are upstream `main`/`latest`, not a pinned or tested project release. Selecting Zephyr does not establish support for every required interrupt boundary. Pin the Zephyr, HAL and board revisions before implementation.

## MPU-6050 prototype assessment

The MPU-6050 can produce nominal 200 Hz data: with DLPF enabled, the 1 kHz base divided by `1 + SMPLRT_DIV` gives 200 Hz at divider four. With DLPF disabled and the 8 kHz base, divider 39 gives 200 Hz; divider four would instead produce 1600 Hz. DLPF selection also changes latency: setting three specifies 4.9 ms accelerometer and 4.8 ms gyro delay. These are configuration examples, not project-tested settings. [InvenSense register map Rev 4.2, sections 4.2–4.3](https://invensense.tdk.com/wp-content/uploads/2015/02/MPU-6000-Register-Map1.pdf).

The [Zephyr binding](https://docs.zephyrproject.org/latest/build/dts/api/bindings/sensor/invensense,mpu6050.html) exposes ranges, divider and `int-gpios`. The [driver initialization](https://github.com/zephyrproject-rtos/zephyr/blob/main/drivers/sensor/tdk/mpu6050/mpu6050.c) sets the divider but does not configure DLPF. Its [trigger code](https://github.com/zephyrproject-rtos/zephyr/blob/main/drivers/sensor/tdk/mpu6050/mpu6050_trigger.c) accepts only `SENSOR_TRIG_DATA_READY` and defers callbacks to a thread/workqueue. Motion setup and early edge capture need extension.

Historical InvenSense documentation describes programmable `MOT_THR`, a motion-duration counter with 1 ms units, and a DHPF/held-reference detector path. That is not automatically a raw absolute-g comparator; 1 ms counter resolution is not total detection latency. These legacy details appear in [register map Rev 3.2, archival manufacturer PDF](https://cdck-file-uploads-europe1.s3.dualstack.eu-west-1.amazonaws.com/arduino/original/3X/8/1/81493bebd267609d186184aa85227a5484bfe829.pdf), while Rev 4.2 omits these motion registers. Verify revision, threshold scaling, detector cadence and concurrent streaming on the actual part.

One shared INT cannot provide separate DRDY and marker wires. A combined implementation must attribute captured edges using status and report unresolved overlaps. I²C is the selected prototype host interface; historical SPI wiring does not apply. Acquisition and networking can be developed on the selected MPU-6050 while hardware-marker acceptance remains open. Software threshold detection would be a different measurement boundary and must not silently replace the agreed hardware-marker goal.

## First-prototype validation gates

1. **Pin and verify the integration.** Record the actual ESP32 board, MPU-6050/module revision, Zephyr/HAL revisions, driver configuration, I²C wiring and shared INT wiring. Build and inspect the selected board/driver combination before claiming support.
2. **Prove nominal 200 Hz operation.** Explicitly configure and read back DLPF and sample divider together; measure sample cadence and loss under load. A divider property alone does not establish 200 Hz. Preserve separate sample identities and the existing per-sample `t0` boundary.
3. **Prove simultaneous sampling and marking.** Extend the reviewed driver path for motion configuration and early edge capture as needed. Validate shared-INT source attribution, status clearing, latching, overlap and rearm without changing acquisition or power modes. No second MPU-6050 interrupt output is assumed. Capture `t_trigger` only at a supported boundary; record later callback timing separately and preserve unresolved cases.
4. **Characterize event meaning and overhead.** Verify the actual part's detector path, threshold units, cadence and duration before calling it an absolute acceleration marker. Measure filtering, capture uncertainty, missed edges, saturation, motor-induced triggers and sample-link races. Apply the [marker contract](imu-trigger-markers.md); marker activity must not gate sends or change per-sample outcomes, priorities or deadlines. Marker metrics and their auditor still require implementation.

Battery operation and ESP32/Zephyr compatibility remain measurement gates. User-reported MPU-6050 availability is useful context, not a verified supplier or board claim. Final production hardware remains open separately from this agreed first-prototype selection.

## Conditions for later alternatives

ST requires both DSV sensors in high-accuracy mode for nominal 200 Hz, with mode transitions from power-down. [AN5763, sections 3.1–3.2](https://www.st.com/resource/en/application_note/an5763-lsm6dsv16x-6axis-imu-with-embedded-sensor-fusion-ai-qvar-for-highend-applications-stmicroelectronics.pdf) documents that selection. Zephyr offers `LSM6DSVXXX_DT_ODR_HA02_AT_200Hz`, but its [binding](https://github.com/zephyrproject-rtos/zephyr/blob/main/dts/bindings/sensor/st,lsm6dsvxxx-common.yaml) says ODR properties alone do not change operating mode. Any later adoption must verify initialization, register readback, cadence and independent routing where available.

208/240 Hz or higher internal ODR experiments are separate configurations. Do not silently resample, discard samples, alter transaction cadence or call them unchanged 200 Hz operation. A different acquisition strategy needs an explicit profile decision and provenance review.

For longer-term procurement, TDK currently lists MPU-6050 as obsolete. This does not rule out a demonstrator using an available module, but supplier stock does not establish ongoing production. [TDK product status](https://product.tdk.com/en/search/sensor/mortion-inertial/imu/info?part_no=MPU-6050).
